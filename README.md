# EDA: выводы по датасету

## Общая структура данных

- `train.parquet` — 497 673 строки, каждая пара «запрос → выбранное объявление» (`search_*` + `item_*` в одной строке)
- `benchmark_queries.parquet` — 2 452 запроса, колонки `search_*` + `query_id`
- `benchmark_items.parquet` — 189 212 объявлений, колонки `item_*`
- В `train` есть `item_id` (тип `string`) — можно напрямую связывать выборы с конкретными объявлениями
- Признаки `search_infm_params_text` и `item_price`/`item_latitude`/`item_longitude` хранятся как `decimal128` — при загрузке переводим в `float64`
- Все id-колонки приводим к строкам (`item_id`, `query_id`, `search_location_id`, `item_location_id`, `item_category_id`, `item_microcat_id`) — защита от несовпадений типов между файлами
- `item_id` — строго 16 символов `0-9a-f`, проверено `assert`, формат соблюдается на 100%

## Пересечение объявлений (train ↔ корпус бенчмарка)

- Уникальных объявлений в train: 344 825
- Из них есть в корпусе бенчмарка: 18 142 (**5,3%**)
- Доля строк train, где объявление есть в корпусе: **6,6%**
- Доля объявлений корпуса, которые хоть раз выбирали в train: **9,6%**

**Вывод:** данные в основном новые. 90% объявлений корпуса не имеют истории выборов в train. Статистика «что выбирали по объявлению» — второстепенный источник, не может быть основным. Решение должно строиться на обобщении (текст, смысл, категория), а не на запоминании конкретных пар.

## Пересечение текстов запросов (train ↔ бенчмарк)

Проверено по уровням строгости (после нормализации текста: lower, ё→е, схлопывание пробелов):

| Уровень | Доля запросов бенчмарка, знакомых train |
|---|---|
| только текст | **37,4%** |
| текст + локация | 6,6% |
| текст + локация + доставка | 6,6% |
| все поля поиска | 4,4% |

**Вывод:** 62,6% запросов бенчмарка вообще не встречались в train по тексту. Пара «текст + локация» знакома лишь в 6,6% случаев — резкий разрыв с 37,4% говорит о том, что один и тот же текст ищут в разных городах. Коллаборативная статистика «запрос → объявление» должна строиться в два уровня: сначала по паре (текст, локация), с откатом на «просто текст» без привязки к городу.

### Примеры незнакомых запросов (качественный разбор)

Незнакомые запросы — не случайный шум, а закономерные вариации:
- **город/район вписан прямо в текст** («шугаринг женский кайеркан», «трансфер до иркутска», «чистка колодцев рощино») — из-за этого текстовое совпадение принципиально не может их поймать
- **длинные, «естественные» формулировки** вместо коротких ключевых слов («вынос без вывоза дивана из квартиры», «услуги психолога оторвать от алкоголя»)
- **опечатки** («сделаслелать губы»)
- **нишевые/специфичные услуги** («натуропат», «изделие на 3д принтере», «аниматор железный человек»)
- **сокращения/аббревиатуры** («репетитор... на жби», «продленка 40 гимн»)

**Вывод:** нужны методы, устойчивые к лишним словам и словоформам — символьные n-граммы (TF-IDF), классификатор подкатегории, dense-эмбеддинги. Точное совпадение текста здесь принципиально бессильно.

## Подкатегории (`item_microcat_id`)

- Всего уникальных подкатегорий: **212**
- Распределение сильно неравномерное (степенное): топ-10 категорий → **27%** строк train; топ-50 → **67,1%**; топ-100 → **89,2%**
- Категорий с < 10 строк: 13 из 212 (6,1% видов), но это всего 29 строк train (**0,01%** от всех данных)

**Вывод:** данных достаточно для обучения классификатора без специальных мер против дисбаланса (`class_weight='balanced'` как лёгкая подстраховка). Редкий хвост категорий погоды не делает. 212 классов — немного, задача классификации вполне решаема TF-IDF + логистическая регрессия.

## Совпадение локации (объявление vs локация поиска)

| `search_is_delivery_search` | Доля совпадений локации | Строк |
|---|---|---|
| 0 (обычный поиск) | **83,1%** | 497 661 |
| 1 (доставка) | 50% (не показательно) | 12 |

**Вывод:** доставки в данных почти нет (12 строк из ~500 тыс.) — любые выводы по ней ненадёжны, фильтр по локации для доставки не применяется вообще (по умолчанию — искать по всему корпусу). Для обычного поиска жёсткий фильтр по точной локации теряет ~17% правильных ответов ещё до всякого текстового поиска.

### Расстояние промахов локации (только обычный поиск)

Среди строк, где локация объявления ≠ локация поиска:

| Процентиль | Расстояние, км |
|---|---|
| 5% | 6,6 |
| 50% (медиана) | 34,4 |
| 75% | 100,3 |
| 90% | 499,3 |
| max | 14 773 |

**Вывод:** половина промахов — это «соседние» случаи (< 35 км, агломерации/районы), которые можно закрыть расширением пула по координатам. Хвост распределения (90%+) — это уже не география (удалённые услуги, шумные данные), фильтром не решается. Выбран **радиус 50 км** как стартовый компромисс.

## Ограничение по координатам локаций

- 273 уникальных `search_location_id` в бенчмарке
- **57 локаций (20,9%)** не имеют ни одного объявления ни в корпусе бенчмарка, ни в train → невозможно вычислить их координаты
- Это затрагивает **425 запросов бенчмарка (17,3%)**
- Все 425 — обычный поиск (0% доставки среди них)

**Вывод:** для 17,3% запросов бенчмарка фильтр по локации не может сузить пул (нет данных о географии) — используется весь корпус (189 212), релевантность для них целиком на текстовых источниках (BM25, dense, классификатор подкатегории). Это задокументированное ограничение состава данных, а не изъян реализации.

## Итоговые архитектурные решения, вытекающие из EDA

1. **Данные в основном новые** → приоритет источникам, которые обобщают (классификатор подкатегории, dense-эмбеддинги, BM25), а не запоминают (статистика по истории выборов — второстепенный источник)
2. **Фильтр по локации** — мягкий: точная локация + соседи в радиусе 50 км (с расширением до 150/500/2000 км, если пул < 300); полностью отключается для доставки; для локаций без известных координат (17,3% запросов) — полный корпус без фильтра
3. **Классификатор подкатегории** — TF-IDF по символьным n-граммам (устойчив к опечаткам/словоформам) + логистическая регрессия, топ-5 предсказанных классов на запрос, `class_weight='balanced'`
4. **Валидация (`val`-часть train)** строится по группам «текст + локация» (не по отдельным строкам), чтобы избежать утечки и максимально повторить условия реального бенчмарка (6,6% знакомых пар)
