# Кандидатогенерация для поиска услуг

Решение задачи отбора до 50 объявлений из корпуса в 189 212 записей для
2452 поисковых запросов. Метрика — **Recall@50** (макро по запросам,
порядок внутри топ-50 не важен).

**Итоговый результат: 0.8466 на валидации, 0.81 на лидерборде.**

Схема решения: 

1. географический фильтр 
2. четыре независимых источника кандидатов 
3. объединение через RRF
4. переранжирование верхушки списка градиентным бустингом.

## Как запустить

Скачать с Яндекс.Диска папки `data/` и `models/` и положить их в корень проекта.

torch ставится отдельно от общего requirements.txt, так как CPU- и GPU-сборки берутся с разных индексов:


```bash
# На CPU-машине (например, для шагов 1, 3–6 — без построения эмбеддингов):
pip install torch==2.14.0 --index-url https://download.pytorch.org/whl/cpu
# На GPU-машине (для шага 2 — build_embeddings.py):
pip install torch==2.14.0
pip install -r requirements.txt
python -u -m app.scripts.predict_reranked   
# answers_rerank.csv в корне
```

## 1. Задача и результат

Дано:

| Файл | Размер | Содержание |
|---|---|---|
| `train.parquet` | 497 673 строки | пары «запрос → выбранное объявление» |
| `benchmark_queries.parquet` | 2 452 запроса | запросы, для которых нужен ответ |
| `benchmark_items.parquet` | 189 212 объявлений | корпус, из которого отбираем |

Требуется для каждого запроса бенчмарка вернуть до 50 `item_id`. Формат
ответа — CSV с колонками `query_id,answer` (id через пробел, без индекса).

Ограничения задания: локальный запуск без внешних API, обязательные
комментарии в коде, запрет на хардкод ответов.

### Отправки

| # | Конфигурация | Валидация | Лидерборд |
|---|---|---|---|
| 1 | RRF, 3 источника (BM25 + e5 + подкатегории) | 0.8091 | 0.7628 |
| 2 | RRF, 4 источника (+ FRIDA) | 0.8231 | 0.7800 |
| 3 | RRF + CatBoost-реранк верхушки | **0.8466** | **0.8100** |

Систематическая поправка валидации к лидерборду — около **−0.04**.
Причина известна и объяснена в разделе 9: валидационная выборка завышена
по доле знакомых запросов (82,2% против 37,4% в бенчмарке).

## 2. Запуск и воспроизводимость

### Окружение

Работа велась на арендованном сервере: **62 ГБ RAM, 38 ядер (CPU)**.
На машине с 16 ГБ построение BM25-индекса по объединению падает с OOM.
Эмбеддинги считались отдельно на **RTX 3090**.

Фиксированный seed проекта: `SEED = 67` (в `app/infrastucture/config.py`).

### Порядок запуска

```bash
# 1. Объединение объявлений корпуса и train → all_items.parquet (515 895 записей)
python -u -m app.scripts.prepare_all_items

# 2. Эмбеддинги двумя моделями (запускать на GPU-машине)
python -u -m app.scripts.build_embeddings

# 3. Обучающая выборка для реранкера (~5 часов при 1.4 запроса/с)
python -u -m app.scripts.build_trainset

# 4. Обучение реранкера на верхушке RRF (~30 сек)
python -u -m app.scripts.train_reranker_head

# 5. Оценка на валидации (первый запуск ~15 мин, дальше из кэша — секунды)
python -u -m app.scripts.eval_reranker_head models/reranker_top150.cbm

# 6. Финальный ответ на бенчмарк (~15 мин) → answers_rerank.csv
python -u -m app.scripts.predict_reranked
```

BM25-индекс строится при первом вызове `Pipeline._setup()` (~300 сек) и
кэшируется в `data/processed/bm25_index.joblib`; последующие запуски
загружают его с диска.

`eval_reranker_head` при первом запуске прогоняет источники по всем 3000
запросам валидации и кэширует признаки верхушки в
`data/processed/val_head_features.pkl`. Все последующие проверки моделей
(другой файл `.cbm`, другое значение `TOP_RERANK`) читают кэш и
отрабатывают за секунды. Кэш нужно удалить при изменении `TOP_N`,
`feature_extractor.py`, состава источников или весов RRF.

### Разбиение данных

`split_train` даёт три непересекающихся сплита: **fit** (343 024 запроса),
**rank** (7 507), **val** (3 000). Валидация используется только для
финальной оценки и никогда не участвует в обучении.

Разбиение делается **по группам «текст запроса + локация»**, а не по
отдельным строкам — иначе один и тот же запрос попал бы и в обучение, и
в оценку, что дало бы завышенный результат.

## 3. Архитектура решения

Одиночный источник кандидатов недостаточен: лучший из них (BM25) даёт
0.7623. Ансамбль через RRF поднимает результат до 0.8231, но упирается в
потолок ранжирования — объединение кандидатов содержит правильный ответ
в 0.9603 случаев. Реранкер поверх RRF частично закрывает этот разрыв.

Отсюда уровни:

1. запрос 
2. фильтр локации (BallTree/haversine, радиусы 50/150/500/2000 км)
3. 4 источника, top_k=500 каждый 
4. RRF(k=60), веса bm25=1.0 / e5=0.75 / frida=0.75 / microcat=0.5 
5. верхушка 150
6. CatBoost-реранк 
7. топ-50

### Фильтр локации

Пул кандидатов сужается географически до вызова текстовых источников.

- Точная локация запроса плюс соседние в радиусе **50 км**, с расширением
  до 150 / 500 / 2000 км, если пул получился меньше 300 объявлений.
- Для доставки (`search_is_delivery_search=1`) фильтр **отключается
  полностью** — в train таких строк всего 12, режим не валидируется.
- Для локаций без известных координат (17,3% запросов бенчмарка)
  используется весь корпус без сужения.

Recall пула после фильтра — **0.988**: фильтр сохраняет практически все
правильные ответы и при этом сокращает медианный пул до 3548 объявлений.

### Источники кандидатов

Каждый возвращает до 500 кандидатов с сырыми скорами.

**BM25** — собственная реализация на разреженных матрицах. Библиотека
`rank_bm25` оказалась слишком медленной для корпуса такого размера.
Ключевая оптимизация: в формуле BM25 всё, кроме факта присутствия терма
в запросе, зависит только от пары (документ, терм), поэтому веса
предпосчитываются один раз в CSC-матрицу, а скоринг запроса сводится к
сложению нужных колонок. Лемматизация — `pymorphy3` с кэшем лемм.
Параметры `k1=1.5`, `b=0.75`, `min_df=2`. Индекс по объединению:
515 895 объявлений, словарь 111 707 термов.

**e5-small** — `intfloat/multilingual-e5-small`, 384 измерения, префиксы
`query: ` / `passage: `. Эмбеддинги нормализованы, поиск — скалярное
произведение (эквивалент косинусной близости).

**FRIDA** — `ai-forever/FRIDA`, 1536 измерений, префиксы `search_query: ` /
`search_document: `. Векторы сохраняются в `float16` — это вдвое
сокращает объём индекса без заметной потери качества поиска.

**Подкатегории** — классификатор `TfidfVectorizer(char_wb, 3–5)` +
`SGDClassifier(log_loss)`, топ-5 предсказанных подкатегорий, внутри них
отбор по популярности. Самый слабый источник (0.4787 в одиночку), но
закрывает запросы, где текстовое совпадение бессильно.

### Объединение (RRF)

Reciprocal Rank Fusion с `k=60` и весами `bm25=1.0`, `e5=0.75`,
`frida=0.75`, `microcat=0.5`. На выходе — **полный** ранжированный
список кандидатов, а не топ-50: он целиком нужен как вход реранкера и
как материал для признаков.

### Реранкер

Верхушка из 150 кандидатов RRF переранжируется CatBoost, хвост остаётся
в исходном порядке. Ограничение верхушкой — осознанный компромисс:
потолок такого реранка равен `Recall@150(RRF) = 0.8961`, зато модель не
может утопить правильный ответ ниже 150-й позиции. Детали — раздел 7.

### Ключевое архитектурное решение

Все индексы (BM25, эмбеддинги, география) строятся **один раз по
объединению** корпуса бенчмарка и уникальных объявлений train — 515 895
записей. Переключение между режимами «искать только в корпусе бенчмарка»
и «искать по всему объединению» делается параметром `restrict_to` в
`get_pool()`, а не пересборкой индексов.

Это даёт главное: функция `_run_sources()` вызывается **одинаково** и на
инференсе, и при сборке обучающей выборки реранкера. Любое расхождение
между этими двумя режимами — прямой путь к модели, которая учится на
одном распределении, а применяется к другому. Именно на этом провалились
первые две попытки реранкера (раздел 7).

## 4. Выводы EDA, определившие архитектуру

### Данные в основном новые

| Показатель | Значение |
|---|---|
| Уникальных объявлений в train | 344 825 |
| Из них есть в корпусе бенчмарка | 18 142 (**5,3%**) |
| Доля строк train с объявлением из корпуса | **6,6%** |
| Доля объявлений корпуса, которые хоть раз выбирали | **9,6%** |

**90,4% объявлений корпуса не имеют истории выборов.** Статистика «что
выбирали по этому объявлению» не может быть основным сигналом — решение
должно строиться на обобщении (текст, смысл, категория), а не на
запоминании конкретных пар.

### Запросы бенчмарка в основном незнакомые

| Уровень совпадения | Доля запросов бенчмарка |
|---|---|
| только текст | **37,4%** |
| текст + локация | 6,6% |
| текст + локация + доставка | 6,6% |
| все поля поиска | 4,4% |

**62,6% запросов бенчмарка вообще не встречались в train по тексту.**
Разрыв между 37,4% и 6,6% говорит, что один и тот же текст ищут в разных
городах.

Незнакомые запросы — не шум, а закономерные вариации:

- город или район вписан прямо в текст («шугаринг женский кайеркан»,
  «чистка колодцев рощино») — текстовое совпадение принципиально
  не поймает такое;
- длинные естественные формулировки вместо ключевых слов («вынос без
  вывоза дивана из квартиры»);
- опечатки («сделаслелать губы»);
- нишевые услуги («натуропат», «изделие на 3д принтере»);
- сокращения («репетитор... на жби», «продленка 40 гимн»).

Отсюда ставка на методы, устойчивые к лишним словам и словоформам:
символьные n-граммы, лемматизация, плотные эмбеддинги.

### География

При обычном поиске локация объявления совпадает с локацией запроса в
**83,1%** случаев. Жёсткий фильтр по точному совпадению потерял бы 17%
правильных ответов ещё до всякого текстового поиска.

Расстояния промахов (только обычный поиск):

| Процентиль | Расстояние |
|---|---|
| 5% | 6,6 км |
| 50% | 34,4 км |
| 75% | 100,3 км |
| 90% | 499,3 км |
| max | 14 773 км |

Половина промахов — соседние населённые пункты внутри агломерации,
что закрывается расширением пула по координатам. Хвост распределения —
уже не география, а удалённые услуги и шум; фильтром не решается.
Радиус 50 км выбран как компромисс.

**57 из 273 локаций бенчмарка (20,9%) не имеют координат** — ни одного
объявления ни в корпусе, ни в train. Это затрагивает **425 запросов
(17,3%)**, и для них релевантность целиком ложится на текстовые
источники.

### Подкатегории

212 уникальных подкатегорий, распределение степенно. Категорий с менее чем 10 строками — 13 из 212, но это всего 29 строк (0,01% данных), то есть редкий хвост погоды не делает.

| Количество категорий | Процентиль покрытия |
|----------------------|---------------------|
| 10                   | 27%                 |
| 50                   | 67,1%               |
| 100                  | 89,2%               |

### Доставка

В train всего **12 строк** с `search_is_delivery_search=1` из ~500 тысяч.
Любые выводы по этому режиму статистически ненадёжны, поэтому фильтр
локации для доставки просто отключается.

## 5. Абляция: вклад каждого компонента

Все значения — Recall@50 на валидации (3000 запросов).

| Этап | Recall@50 |
|---|---|
| Случайный выбор 50 из пула | 0.0141 |
| Популярность (baseline) | 0.0416 |
| Подкатегории + популярность | 0.4787 |
| BM25 один | 0.7623 |
| e5 один | 0.7559 |
| RRF, 3 источника | 0.8091 |
| RRF, 4 источника (+ FRIDA) | 0.8231 |
| **RRF + CatBoost-реранк верхушки 150** | **0.8466** |
| *Потолок: объединение кандидатов (union)* | *0.9603* |
| *Потолок: пул после фильтра локации* | *0.9880* |

### Покрытие источников (recall без обрезки до 50)

Показывает, насколько глубоко источник вообще находит правильный ответ —
в отличие от Recall@50, который проверяет ещё и качество ранжирования.

| Источник | @300 | @500 |
|---|---|---|
| BM25 | 0.8807 | 0.8960 |
| Dense | 0.8892 | 0.9154 |
| Подкатегории | 0.6741 | 0.7131 |
| **Union (объединение)** | **0.9408** | **0.9527** |
| Размер union (медиана / среднее) | 473 / 506 | 712 / 787 |

Это разложение определило приоритет работы. Разрыв union на RRF@50
составлял 0.9527 − 0.8091 = **0.144**, тогда как разрыв union - потолок
локации всего 0.988 − 0.9527 = 0.035. Значит, основная потеря происходит
**не на генерации кандидатов, а на ранжировании**: правильный ответ
находится, но не попадает в топ-50 из пула в ~700 кандидатов.

Отсюда вывод: реранкер — приоритетная задача с потенциалом до +0.14,
что заметно больше, чем возможный выигрыш от дообучения энкодеров
(до +0.035 по покрытию).

## 6. Подбор гиперпараметров

### Вес подкатегорий в RRF

| `w_microcat` | 0.0 | 0.25 | **0.5** | 0.75 | 1.0 |
|---|---|---|---|---|---|
| Recall@50 | 0.7621 | 0.7808 | **0.7862** | 0.7807 | 0.7613 |

Подкатегории — слабый источник, при большом весе тянут результат вниз
(при весе 1.0 итог даже хуже, чем у BM25 в одиночку). Но при весе 0.5
они закрывают пробелы, которые не ловятся лемматизированными термами.

### Параметр сглаживания RRF

| `k` | 10 | 20 | 40 | **60** | 100 |
|---|---|---|---|---|---|
| Recall@50 | 0.8038 | 0.8077 | 0.8084 | **0.8091–0.8102** | 0.8084 |

Кривая плоская, дальше не тюнится. Значение 60 — стандартное из
литературы и одновременно оптимум на этих данных.

### Глубина источников

Переход с `top_k=300` на `top_k=500` почти не меняет RRF@50
(0.8102 -> 0.8091, в пределах шума), но заметно поднимает покрытие
union (0.9408 -> 0.9527). Глубина 500 зафиксирована не ради самого RRF,
а как материал для реранкера.

## 7. Реранкер: три неудачные попытки и их диагностика

Первые три попытки дали результат **хуже** чистого RRF, и причина каждый раз оказывалась не в модели, а в данных, на которых она обучалась.

### Мотивация

Объединение кандидатов содержит правильный ответ в 0.9603 случаев,
RRF достаёт 0.8231. Разрыв 0.14 — это чистые потери на ранжировании.

### Попытка 1: обучение на неправильном распределении пулов

Обучающая выборка собрана с `restrict_to=None` — то есть пулы кандидатов
формировались из полного объединения, а не из корпуса бенчмарка.
25 000 запросов -> 23 340 групп, 730 904 строки.

**Результат: 0.6708** — заметно хуже RRF.

### Попытка 2: удаление подозрительных признаков

Убраны `pool_size`, `n_candidates` и флаги `*_found` (их важность была
нулевой — информация дублировала `NaN` в соответствующем ранге).

**Результат: 0.6317** — ещё хуже.

### Диагноз попыток 1–2

Замеры показали, что обучающие пулы не воспроизводят инференсные:

- **`pool_size`**: медиана 6044 на обучении против ~3548 на инференсе —
  пулы из объединения почти вдвое крупнее.
- **`n_candidates` был сломан**: считался *после* негативного сэмплинга
  и всегда равнялся 31 вместо реальных ~700. Признак не падал с ошибкой,
  он молча содержал неверное значение.
- **География схлопывалась**: `distance_km` + `same_location` давали 24%
  важности модели. На обучении пул включал объявления на расстоянии до
  13 120 км (медиана позитивов 2,77 км против 6,40 у негативов) — сигнал
  «ближе значит вероятнее» был мощным. На инференсе пул уже отфильтрован
  географически, все кандидаты близко, и сигнал перестаёт различать.

### Попытка 3: совмещение режимов

Выборка пересобрана с `restrict_to=bench_ids` — тот же режим, что на
инференсе. `n_candidates` починен через параметр `n_candidates_total`.
Взяты только `eligible`-запросы (те, чьи выбранные объявления есть
в корпусе).

**Результат: 0.72** — лучше, но всё ещё ниже RRF 0.8231.

### Ограничение реранка верхушкой

Следующая гипотеза: применять модель только к верхушке RRF, чтобы она
физически не могла утопить кандидата ниже её границы.

Потолок такого подхода равен `Recall@N(RRF)`:

| k | 50 | 75 | 100 | 150 |
|---|---|---|---|---|
| RRF Recall@k | 0.8231 | 0.8576 | 0.8746 | **0.8961** |

То есть в топ-150 лежит 0.8961 правильных ответов — максимум, который
можно получить, переставляя только эту часть списка.

Результат модели попытки 3 на верхушке:

| `TOP_RERANK` | 75 | 100 | 150 |
|---|---|---|---|
| Recall@50 | 0.7422 | 0.7231 | 0.7176 |

**Качество падает с ростом верхушки.** Это оказалось решающей подсказкой:
если бы модель просто была слабой, результат бы колебался вокруг RRF.
Монотонное ухудшение означает, что сигнал модели **инвертирован** —
чем больше кандидатов ей доверяешь, тем хуже.

### Настоящая причина: смещение негативного сэмплинга

`TrainsetBuilder._sample()` для каждого запроса брал:

- **все позитивы**, на любом ранге RRF;
- **15 «трудных» негативов** — первые не-позитивы в RRF (ранги ~1–16);
- **15 случайных негативов** из оставшихся ~680.

Такая схема выглядит разумной (трудные негативы — стандартный приём),
но она создаёт перекос по рангам. На рангах 1–15 негативов много, потому
что туда попадают все трудные. На рангах 20–150 негативов почти нет:
случайных приходится примерно 1–3 на группу против ~130 реальных
кандидатов. Позитивы при этом сохранены везде.

Доля позитивов по рангам RRF в обучающей выборке:

| Ранг RRF | Строк | Доля позитивов | С поправкой весами |
|---|---|---|---|
| 1–15 | 222 375 | 0.0466 | 0.0466 |
| 15–30 | 15 687 | **0.1092** | 0.0078 |
| 30–50 | 6 084 | **0.1506** | 0.0031 |
| 50–100 | 13 746 | 0.0681 | 0.0013 |
| 100–150 | 13 193 | 0.0268 | 0.0005 |
| 150–500 | 88 590 | 0.0082 | 0.0001 |
| 500+ | 100 424 | 0.0033 | 0.0000 |

**На рангах 30–50 доля позитивов втрое выше, чем в топ-15.** Модель
честно выучила то, что видела: середина списка лучше его верха. Отсюда
и инвертированный сигнал, и монотонное ухудшение с ростом верхушки.

### Исправление: веса вместо пересборки данных

Пересобирать выборку (5 часов) не потребовалось. Каждый случайный
негатив «представляет» всех невыбранных на своём участке списка, поэтому
достаточно взвесить его обратной вероятностью попадания в выборку:

```
вес случайного негатива = (негативов вне трудных) / (сколько из них взяли)
```

Средний вес получился **64,7**. Колонка `weight` передаётся в
`catboost.Pool`. После поправки доля позитивов монотонно убывает с
рангом — как и должно быть в реальности (правая колонка таблицы выше).

Выборка дополнительно фильтруется по `rrf_rank < 150`, чтобы обучающее
распределение совпало с инференсным режимом реранка верхушки.

| Этап | Строк | Групп |
|---|---|---|
| `trainset_v2` (fit) | 280 788 | 9 047 |
| `evalset_v2` (rank) | 179 311 | 5 778 |
| Объединение | 460 099 | 14 825 |
| После фильтра по верхушке | 253 688 | 13 788 |

Доля позитивов в итоговой выборке — 0.056.

### Результат после исправления

| `TOP_RERANK` | 75 | 100 | 150 |
|---|---|---|---|
| Recall@50 | 0.8402 | 0.8436 | **0.8466** |

**Тренд развернулся**: теперь чем больше верхушка, тем лучше результат —
модель действительно достаёт правильные ответы с позиций 51–150, а не
портит верх списка. Прирост к чистому RRF: **+0.0235**.

| Признак | Важность |
|---|---|
| `rrf_score` | 13.14 |
| `rrf_rank` | 12.34 |
| `same_location` | 10.80 |

Признаки RRF вышли на первое место — это правильное поведение: модель

### AUC не равен Recall@50

Проверка более длинного обучения:

| Модель | Итераций | AUC (holdout) | Recall@50 (val) |
|---|---|---|---|
| `reranker_top150` | 2 000 | 0.7652 | **0.8466** |
| `reranker_top150_long` | 5 000 | 0.7771 | 0.8454 |

AUC вырос на 0.012, а целевая метрика не улучшилась. Причина в том, что
AUC измеряет порядок всех пар кандидатов, тогда как Recall@50 зависит
только от того, кто оказался по какую сторону 50-й позиции. Дальнейший
рост AUC шёл за счёт перестановок, не влияющих на эту границу.

**Практический вывод:** выбор модели делается по Recall@50 на валидации,
AUC используется только как индикатор, что обучение вообще идёт.

### Признаки реранкера

24 признака, единая точка расчёта — `FeatureExtractor.extract()`,
вызывается и при сборке выборки, и на инференсе:

- **позиции и скоры источников**: `bm25_rank`, `bm25_score`, `e5_rank`,
  `e5_cos`, `frida_rank`, `frida_cos`, `microcat_rank`, `rrf_rank`,
  `rrf_score` + флаги `*_found`;
- **тематика**: `microcat_proba`, `is_top1_microcat`,
  `microcat_pos_in_pred`;
- **свойства объявления**: `reviews_count`, `rating`, `popularity_rank`;
- **география**: `distance_km`, `same_location`;
- **контекст запроса**: `pool_size`, `n_candidates`, `query_len_tokens`.

Отдельное решение: если источник не вернул кандидата, его ранг
записывается как `NaN`, а **не** как 999 или −1. CatBoost обрабатывает
пропуски нативно (отправляет в отдельную ветку дерева), тогда как любое
число модель проинтерпретирует как осмысленную позицию.

## 8. Что проверено и отвергнуто

### Подкатегории как жёсткий фильтр пула

Гипотеза: сузить пул до топ-5 предсказанных подкатегорий, а BM25
применять уже внутри.

| Вариант | Recall@50 |
|---|---|
| Подкатегории + популярность | 0.4787 |
| BM25 по полному пулу локации | **0.7621** |
| BM25 внутри подкатегорий | 0.6937 |

Проверено на `top_k_classes` = 5 / 10 / 15 / 20 — BM25 по полному пулу
локации всегда лучше. Сужение сокращает медианный пул с 3548 до 118
объявлений, и у 27,2% запросов остаётся меньше 50 кандидатов, то есть
отбирать уже не из чего.

При этом сам классификатор работает хорошо: потолок Recall после сужения
0.8366 при Accuracy@5 = 0.8550 — разрыв всего 0.018, то есть сужение
почти не теряет правильные ответы, попавшие в топ-5 предсказаний.
Основная потеря (0.8366 → 0.4787) происходит на отборе топ-50 внутри
суженного пула слабым сигналом популярности.

Итог: подкатегории оставлены как **источник в RRF**, а не как фильтр.

### LogisticRegression для классификатора подкатегорий

`LogisticRegression(solver="saga")` не сходился — величина изменения
скакала в диапазоне 0,6–2,0 на протяжении 32+ эпох без признаков
стабилизации.

Заменён на `SGDClassifier(loss="log_loss", max_iter=15, tol=1e-3,
class_weight="balanced")` — сходимость за 6 эпох (~3,3 минуты).

Итоговые метрики классификатора (на 3248 строках):

| Метрика | Значение |
|---|---|
| Accuracy@1 | 0.6324 |
| Accuracy@5 | 0.8550 |

### rank_bm25

Готовая библиотека оказалась непрактично медленной на корпусе в 515 895
документов. Заменена на собственную реализацию с предпосчётом весов в
разреженную матрицу (см. раздел 3).

### Популярность как основной сигнал

Recall@50 = 0.0416 против 0.0141 у случайного выбора. Число отзывов —
слабый сигнал, рейтинг почти не различает объявления. Оставлена как
признак реранкера (`popularity_rank`, важность ниже топ-10) и как
запасной вариант, когда BM25 не находит ни одного терма запроса.

## 9. Ограничения и направления развития

### Известные ограничения

**Валидация систематически завышена.** Доля знакомых текстов запросов
в val — 82,2% против 37,4% в бенчмарке. Разбиение по группам
«текст + локация» прячет утечку конкретной пары, но не утечку самого
текста запроса. Отсюда стабильная поправка val → лидерборд около −0.04,
которую нужно учитывать при интерпретации любых чисел выше.

**17,3% запросов без географии.** Для 425 запросов бенчмарка координаты
локации неизвестны, пул не сужается, и релевантность целиком зависит от
текстовых источников. Это ограничение состава данных, а не реализации.

**Режим доставки не валидируется.** 12 строк в train — статистически
ничто. Текущее решение (отключать географический фильтр) основано на
здравом смысле, а не на данных.

**Разрыв до потолка остаётся.** 0.8466 против 0.9603 у объединения
кандидатов и 0.9880 у пула после фильтра локации.

### Что не проверено из-за нехватки времени

- **Смешивание рангов реранкера с RRF** вместо полной замены порядка:
  комбинировать по формуле RRF ранг модели и ранг фьюжна. Модель тогда
  может только подвинуть кандидата, но не утопить его. Пересечение
  финального ответа с ответом чистого RRF составило 0.814 в среднем и
  0.220 в минимуме — то есть на отдельных запросах модель перетасовывает
  почти весь топ-50, и более мягкая схема могла бы дать прирост.
- **Разбор метрики по срезу «знакомый / незнакомый запрос»** — понять,
  где именно реранкер выигрывает. Если весь прирост приходится на
  знакомые запросы, на лидерборде он будет заметно меньше.
- **Дообучение e5 на домене** — потенциал до +0.035 по покрытию union.
- **Кросс-энкодер на топ-50** — дорого по времени инференса, но это
  следующий естественный шаг после градиентного бустинга на признаках.
- **Расширение верхушки реранка выше 150** — потолок продолжает расти
  (`Recall@150 = 0.8961` против `Recall@100 = 0.8746`), но требует
  пересборки кэша признаков.

## 10. Инженерные заметки

В проекте несколько раз ловились ошибки, которые **не падали с
исключением, а молча портили метрику**. Список того, что было найдено:

| Ошибка | Последствие |
|---|---|
| Регулярка токенизации без кириллицы | BM25 не видел русские слова |
| `argsort` без минуса | сортировка по возрастанию скора вместо убывания |
| Передача всей матрицы вместо одной строки | скоринг по чужому вектору запроса |
| `n_candidates` считался после сэмплинга | признак всегда равен 31 вместо ~700 |
| Смещение негативного сэмплинга по рангам | инвертированный сигнал модели (раздел 7) |

Ни одна из них не проявлялась как ошибка выполнения — все давали
корректно выглядящий результат с испорченным качеством.

### Защиты, добавленные в код

**Проверка выравнивания признаков и кандидатов.** Перед вызовом
`predict_proba` явно проверяется, что строки матрицы признаков
соответствуют тем `item_id`, для которых они считались:

```python
assert set(ids) == set(candidates), "id строк X не совпадают с кандидатами"
```

**Контрольное значение в каждом прогоне оценки.** Скрипт
`eval_reranker_head` печатает `RRF Recall@50`, которое должно равняться
0.8231. Любое расхождение означает, что что-то в конвейере разъехалось,
и результаты модели в этом прогоне недостоверны.

**Проверка формата ответа перед отправкой.** `predict_reranked` читает
сохранённый CSV заново — так же, как его прочитает проверяющая система —
и проверяет: 2452 строки, корректные колонки, не более 50 id на запрос,
отсутствие дубликатов, все id принадлежат корпусу бенчмарка.

**Сравнение с предыдущей отправкой.** Считается пересечение нового
ответа с ответом чистого RRF. Резкое падение этого показателя означало бы
сбой (например, сдвиг индексов), даже если формально файл корректен.

Результат проверок финального ответа:

```
Формат ОК: 2452 строк, длина ответа медиана 50, мин 50, пустых 0
Пересечение с RRF-ответом: среднее 0.814, мин 0.220
```

**Проверка непересечения выборок.** При объединении `trainset_v2` и
`evalset_v2` явно проверяется, что группы запросов не пересекаются —
иначе один запрос попал бы и в обучение, и в контроль.

**Отложенная выборка по группам, а не по строкам.** Early stopping
использует отложенные `group_id` целиком: если разделять по строкам,
кандидаты одного запроса окажутся по обе стороны разбиения, и контрольная
метрика будет завышенной.
